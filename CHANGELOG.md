# Changelog

## Unreleased

- Fixed: `function_create` no longer splits or shrinks an existing function (#4). It now rejects an address inside an existing function's body (`地址位于已有函数 <name>（入口 <entry>）的函数体内：<address>`) and an entry whose body would overlap an existing function (`新函数体将与已有函数 <name>（入口 <entry>）重叠：<address>`, naming the first such function). The body is the one Ghidra computes from the entry, extended by a read-only pseudo-disassembly of bytes that are not disassembled yet, which is what the next `analysis_run` would grow the new function into; any overlap is rejected, including cases where Ghidra would only have trimmed the new function. An entry whose bytes do not decode as an instruction is rejected too (`入口处的字节无法解码为指令：<address>`). Calls are not followed into the callee, but their targets are resolved (direct calls from the flow; indirect calls from the listing's call references or by reading the pointer in memory with the program's pointer size and byte order), and a target inside an existing function's body that is not its entry is rejected (`新函数中的调用目标位于已有函数 <name>（入口 <entry>）的函数体中部：<address>`), because analysis creates a function at every call target and would split that function. After a call to a noreturn function, or a call Ghidra marks as not falling through, the prediction does not continue into the following bytes. Nothing is changed when `function_create` rejects. Previously Ghidra's `CreateFunctionCmd` silently moved the overlapping addresses out of the existing function into the new one, and a later `function_delete` left them unassigned, which persisted in the project. Creating a function at a free address, at the entry of a deleted function, or in front of a function whose entry the new code flows into works as before. Programs already damaged this way are not repaired; use `function_body_add` to give the unassigned range back to its function. Limits: `function_create` only guarantees that creating the function does not change another function and rejects the entries its prediction sees would split one; `analysis_run` may still adjust existing functions afterwards, and its behaviour is unchanged. Flows that only analysis discovers (for example switch tables or jumps computed through registers) are not predicted, an indirect call whose target cannot be resolved (for example `call rax` or an unreadable pointer) is allowed, the prediction stops with a rejection after 20,000 instructions, and only x86-64 was tested (ARM/Thumb were not).
- Fixed: a stdio server that had started the JVM (for example after `program_open`) no longer stays alive after stdin EOF. The JVM was created on a tool worker thread that ended without detaching, so JPype's `DestroyJavaVM` at interpreter exit waited for it forever; the JVM is now started on a short-lived helper thread that detaches before it ends.
- Fixed: SIGTERM (including `docker stop`) now runs the same shutdown as stdin EOF in both stdio and Streamable HTTP mode: stop the transport, let running tool calls finish, then `close_all` tries to save and close every open program. Previously the JVM's own SIGTERM handler (or, before the JVM started, the default action or uvicorn's re-raised signal) ended the process without `close_all`, so with several workers more than one program could be cut off mid-transaction or mid-save. The process still exits with status 143 after a SIGTERM; a second SIGTERM during the drain is logged and ignored, and the drain has no time limit (SIGKILL still interrupts it). Shutdown progress is logged (`close_all: closing N open program(s)` / `close_all: finished, …`). Saving on shutdown is best effort: if `close_all` raises, the process logs a traceback and exits with status 1, and the program that failed is not saved; for roughly the first one to two seconds after the JVM starts (during the first `program_open`), the JVM still handles SIGTERM itself and the process exits at once without the drain or `close_all`, usually with status 143 but sometimes with status 134 after a JVM crash (with an `hs_err_pid*.log` in the working directory); SIGINT and SIGHUP are not covered (once the JVM has started they exit with status 130 and 129 without `close_all`; before it starts SIGHUP kills the process at once, and SIGINT ends it only after the transport stops, which in stdio mode means the process waits for the next stdin message or EOF, and that message gets no reply). See the new Shutdown section in the README.
- Fixed: tool worker threads have a Java context class loader again. Starting the JVM on a detached helper thread (above) left every worker attached by JPype with a null context class loader, including the single default worker, which used to create the JVM and had `ghidra.GhidraClassLoader`. Each tool call (and the shutdown `close_all`) now sets the system class loader (`GhidraClassLoader` under PyGhidra) on its worker when the worker has none, so Java code that uses the context class loader without a null check (for example `getContextClassLoader().getResource(...)`) works again, and Java threads that Ghidra starts from a worker (such as the analysis and decompiler pools) inherit `GhidraClassLoader` instead of null, as before SAF-19.
- Fixed (SAF-19 low-priority follow-ups): a SIGTERM that the JVM forwards while `sys.stdin` has no file descriptor (ghidra-mcp embedded in another application, stdio mode) is no longer swallowed; with no transport it can stop from the JVM signal thread, ghidra-mcp now hands the signal back to the JVM's own handler (exit 143 without the drain), as before SAF-19. When the SIGTERM handler that `run()` replaced was installed outside Python, `run()` now restores the default action instead of leaving a handler that ignores every later SIGTERM. When `run()` ends with an error, the stdin copying thread is stopped and no longer reads fd 0 afterwards, not even input that arrives while it is finishing its last 0.25 s poll.
- The error returned to MCP clients when the configured Ghidra is older than the minimum supported version no longer includes the absolute Ghidra installation directory; it reports only the detected version, the minimum version, the reason, and upgrade guidance. The installation directory is written to the server log (logger `ghidra_mcp.runtime`) instead, so remote Streamable HTTP clients no longer learn host filesystem paths from this error.
- The other errors that reach MCP clients no longer include absolute host paths either. A missing Ghidra installation directory, an unreadable or invalid `application.properties`, and an input path outside `GHIDRA_MCP_INPUT_ROOT` now return path-free messages and log the paths on `ghidra_mcp.runtime`; a missing input binary echoes the path the client sent, normalised by pathlib (for example `a//b/./c/` becomes `a/b/c`) but not resolved against the working directory, instead of its resolved absolute form. Errors that ghidra-mcp does not word itself (Java exceptions from Ghidra, `OSError`, PyGhidra start-up failures, and similar) are returned unchanged unless their text contains something that looks like a host path (an absolute POSIX path, a well-known root such as `/home/` or `/srv` even right after other text, a Windows drive, UNC or root-relative `\Users\...` path, a `~/` or `~user/` home directory) or one of the configured Ghidra installation, storage or input roots (as configured or resolved); in that case the client gets the error type (and, for `OSError`, the reason) and the full text is logged on `ghidra_mcp.server`. The check is deliberately conservative: a foreign error that contains an `http(s)://` URL or a Ghidra category or data type path such as `/Demangler/foo` is hidden the same way. The wording of these errors changed, so clients that match on the old text need updating: the path-free messages above are new, and a hidden error now reads `Error executing tool <name>: <ErrorType>：[<reason>；]错误详情包含服务端路径，已对客户端隐去，完整信息见服务端日志`. Successful `program_open` and `program_list` results still report the resolved binary path.

## 20261019.2

- **Breaking change for self-hosted installations:** raised the minimum supported Ghidra version from 12.1.2 to 12.1.3. `ghidra-mcp` now refuses to start the JVM against Ghidra 12.1.2 or older and reports the detected version, the installation directory, the minimum version, and the reason. Ghidra 12.1.3 fixed a potential path-traversal vulnerability when importing XML `*.bytes` files (GP-7064) and an ELF importer regression introduced in 12.1.2 that could fail when processing the dynamic GNU hash table and symbol table (GP-7061). Upgrade Ghidra and point `GHIDRA_INSTALL_DIR` at the new installation before upgrading `ghidra-mcp`.
- Upgraded the Ghidra bundled in the container image from 12.1.2 to the official 12.1.4 release (`ghidra_12.1.4_PUBLIC_20260921.zip`, SHA-256 `ddac49f903da9d5bac833e5cc79395098b9c33cfd3279be5f31bd00387d2d4db`). Ghidra 12.1.4 also fixes a potential `DomainObjectLockedException` (GP-7190), potential stack overflows in the OMF and PE loaders (GP-7173, GP-7205), and stops loading libraries whose location a binary specifies with a UNC path (GP-7176).

## 20261019.1

- Security: upgraded `mcp` 1.28.1 → 1.30.0 to fix GHSA-84m7-p3x7-pcfv / CVE-2026-59951 (stateful Streamable HTTP sessions were never reclaimed, allowing unbounded memory growth), and raised the minimum supported `mcp` to 1.30.
- Security: upgraded the transitive dependencies `pyjwt` 2.13.0 → 2.15.1 and `cryptography` 49.0.0 → 50.0.2 to clear published advisories.
- Explicitly set `AuthSettings.validate_token_resource=False` for the static Bearer token verifier; behavior is unchanged and the new `mcp` deprecation warning is silenced.
- Behavior change from the `mcp` 1.30 defaults in Streamable HTTP mode: request bodies larger than 4 MiB are rejected with HTTP 413, stateful sessions with no request in flight for 30 minutes are closed (an open GET stream keeps a session alive; requests to an expired session get HTTP 404 and the client must initialize again), and at most 10,000 sessions are kept at once (new sessions beyond that get HTTP 503). ghidra-mcp does not override these defaults.
- Capped `requires-python` at `<3.14` because `pyghidra` 3.1.0 pins `JPype1==1.5.2`, which publishes no CPython 3.14 wheels; supported versions are Python 3.11–3.13, and `.python-version` pins local development to 3.12.
